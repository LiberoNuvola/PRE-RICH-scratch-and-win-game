# Treasury distribution specification

## 1. Goal

The treasury should collect funds generated by ticket sales, mint fees, and other platform charges, then automatically redistribute them once a configured threshold is reached.

The target behavior is:
- accumulate all fees in one treasury script UTxO
- trigger a distribution transaction when `treasuryBalance >= threshold`
- separate funds into a small set of fixed destinations
- pay a reward to the relayer that triggers the distribution

## 2. Conceptual design

### Treasury script
The treasury is a script UTxO that stores the policy for redistribution in its datum.

Datum fields:
- `thresholdLovelace`: minimum ADA to trigger a distribution
- `prizePct`: percentage of total treasury for the prize pool, in basis points
- `stakePct`: percentage for staking/reserve allocation
- `reservePct`: percentage for reserve / operational buffer
- `relayerRewardPct`: percentage reserved for the relayer
- `prizeAddress`: public key hash or address for prize pool recipient
- `stakeAddress`: address for staking or future reward pool
- `reserveAddress`: address for reserve / business wallet
- `lastTrigger`: last distribution block/slot
- `version`: distribution policy version

Example values:
- threshold = 10 ADA
- prizePct = 5000 (50.00%)
- stakePct = 3000 (30.00%)
- reservePct = 1950 (19.50%)
- relayerRewardPct = 50 (0.50%)

### Validation rule
When the treasury is triggered:
- the tx must consume the treasury UTxO
- the total treasury lovelace input value must be >= threshold
- the tx must produce outputs to the configured destinations with values proportional to the percentages
- the relayer reward must be included
- the output datum must be updated with the new `lastTrigger` and the same policy

### Why this structure works
The logic is simple and auditable:
- no hidden admin decision inside the browser
- distribution is deterministic once the threshold is reached
- relayer is incentivized but not privileged

## 3. Data flow

1. User buys a ticket.
2. Ticket tx sends a fee to the treasury address.
3. The treasury accumulates ADA / token value.
4. A relayer polls the treasury address.
5. If the treasury is above threshold, the relayer builds the distribution tx.
6. The distribution tx sends funds to the configured destinations.
7. The treasury datum updates to reflect the new distribution cycle.

## 4. Relayer incentive
The relayer is rewarded with a small portion of the treasury, for example 0.5%.
This makes the system self-sustaining: a bot can watch the treasury and call the distribution without manual intervention.

The relayer reward is not a secret admin privilege; it is part of the treasury policy.

## 5. Ad-slot monetization policy
As an additional monetization path, ad slots can be sold as time-based leases. The pricing model should favor a low initial entry price and a simplified package structure instead of per-minute billing.

### 5.1 Price model
The base pricing unit is USDM. The acceptable payment rails are:
- USDM directly
- ADA with equivalent USDM valuation
- PRE with equivalent USDM valuation

The contract should define the required amount as a USDM-equivalent value and accept ADA or PRE only if the value at the time of the tx is at least the required level.

### 5.2 Recommended pricing packages
For the initial rollout, prefer preset packages instead of minute granularity:
- 1 hour
- 6 hours
- 1 day
- 3 days

Suggested starting values:
- 1h = 1.5 USDM
- 6h = 7.5 USDM
- 1d = 12 USDM
- 3d = 30 USDM

This keeps the initial price low and the UX clear.

### 5.3 Dynamic pricing rule
After initial traction, the system can automatically adjust the base price using a controlled band:
- floor price: minimum reachable price
- ceiling price: maximum reachable price
- price step: fixed increment/decrement amount

Example:
- floor = 1.0 USDM / 1h
- ceiling = 10.0 USDM / 1h
- step = 0.5 USDM / 1h

Adjustment logic:
- if a slot is frequently sold and demand is high, the price increases by one step up to the ceiling
- if a slot stays unsold for a sustained window, the price decreases by one step down to the floor
- the change is deterministic and based on aggregate occupancy / sales, not ad hoc manual edits

This provides a market-like behavior without making the system unpredictable.

### 5.4 Time-based leasing rule
The payment relationship is:
- total paid in USDM = package price
- lease duration = selected package duration
- slot becomes unavailable until `now + duration`
- when the lease expires, the slot becomes available automatically and the countdown resets

This satisfies the rule: total paid = total time the ad remains visible.

### 5.5 On-chain validation
The validator should enforce:
- slot exists and can be leased
- selected package matches a valid fixed duration
- required USDM value matches the selected package
- ADA or PRE payment is accepted only if the equivalent valuation meets the requirement
- the new expiry is computed from the selected duration and current slot
- the treasury receives the payment

## 6. Preprod default policy
The following values are the working defaults for the first preprod configuration. They are intentionally conservative and designed to avoid fee erosion and premature treasury drains.

### 6.1 Treasury trigger threshold
- threshold = 25 ADA

The treasury should not distribute until the net treasury value reaches at least 25 ADA.

### 6.2 Distribution split
- 50% prize pool
- 30% reserve / staking pool
- 19.5% operational reserve
- 0.5% relayer reward

This split should be encoded in the treasury datum and reviewed before production.

### 6.3 Fee policy
- claim fee budget = 0.25 ADA per claim
- distribution fee budget = 0.5% of the distributed amount, minimum 0.2 ADA
- winner claim is net of claim fee; the protocol funds the fee, not the user
- treasury threshold is measured on the net value received into treasury, not on the full input amount after network fees

This prevents the reward from being silently consumed by tx costs.

### 6.4 Ad-slot pricing defaults
- 1h = 1.5 USDM
- 6h = 7.5 USDM
- 1d = 12 USDM
- 3d = 30 USDM

Dynamic pricing range:
- floor = 1.0 USDM / hour
- ceiling = 10.0 USDM / hour
- step = 0.5 USDM / hour

These values are intentionally low during early traction and can be raised only via deterministic policy rules.

## 7. Multi-asset handling
Initially, the simplest and safest design is:
- treasury accumulates ADA first
- distribution happens in ADA
- token-based pools can be funded later via separate governance-controlled transactions

If PRE / USDM distribution is required later, the distributor can:
- swap off-chain through a DEX,
- or keep asset-specific pools and route them separately,
- or add another treasury script dedicated to tokens.

For the first production version, prefer ADA-only treasury distribution and token funding as a second phase.

## 7. Operational safety
- keep treasury addresses and payout addresses in configuration, not in browser code
- use a relayer service with logging and retry
- make sure no user-facing UI has authority to move treasury funds
- keep admin keys offline

## 8. Recommended implementation order

1. implement treasury validator with threshold and payout checks
2. implement relayer reference to trigger distribution
3. add admin scripts to initialize treasury and pool funding
4. deploy to preprod
5. validate distribution, retry, and relayer reward logic

## 9. Minimal pseudocode

```text
if treasuryBalance >= threshold then
  distribute prizeShare to prizeAddress
  distribute stakeShare to stakeAddress
  distribute reserveShare to reserveAddress
  distribute relayerReward to relayerAddress
  update treasury datum with lastTrigger
```

This is intentionally deterministic and easy to audit.
