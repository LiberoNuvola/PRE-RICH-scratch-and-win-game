3. B1 ECONOMIC MODEL
================================================================================

  Genesis price and USDM sub-unit convention:
    1 USDM = 100 sub-units (Integer on-chain).
    Genesis ticket: pdPriceUsdm = 100.
    ADA settlement: TICKET_PAYMENT_LOVELACE = 1_000_000 (1 ADA on Preprod).
    The two unit systems are INDEPENDENT. Payouts are in USDM sub-units.
    ADA settlement is in lovelace. They must not be mixed in arithmetic.

  Ticket classes (pdPriceUsdm sub-units):
    Genesis:    100  (1.00 USDM)
    Class 1:    200  (2.00 USDM)
    Class 2:    300  (3.00 USDM)
    Class 3:    500  (5.00 USDM)
    Class 4:   1000  (10.00 USDM)
    Class 5:   2500  (25.00 USDM)
    Class 6:   5000  (50.00 USDM)
    Class 7:  10000  (100.00 USDM)

  Payout table (defaultPrizeTable):
    Tier 0 (loss): base=0,  payout = 0
    Tier 1 (3+ of sym 1): base=2,    payout = base * priceUsdm / 2
    Tier 2 (3+ of sym 2): base=5,    payout = base * priceUsdm / 2
    Tier 3 (3+ of sym 3): base=10,   payout = base * priceUsdm / 2
    Tier 4 (3+ of sym 4): base=200,  payout = base * priceUsdm / 2
    Tier 5 (3+ of sym 5): base=1000, payout = base * priceUsdm / 2

    Genesis examples:
      Tier 1: 2*100/2 = 100 sub-units (1.00 USDM)
      Tier 2: 5*100/2 = 250 sub-units (2.50 USDM)
      Tier 3: 10*100/2 = 500 sub-units (5.00 USDM)
      Tier 4: 200*100/2 = 10000 sub-units (100.00 USDM)
      Tier 5: 1000*100/2 = 50000 sub-units (500.00 USDM)

  EffectivePool:
    effectivePool = totalLiquidity - pendingLiabilities - unresolvedReserve
                    - lockedJackpot
    Must be >= 0 at all times (solvency invariant).
    Jackpot is active when effectivePool >= jackpotThreshold.

  Pending liabilities (ppPendingLiabilities):
    Sum of crystallised, unclaimed winning payouts.
    Increases on TicketRevealed (by payout amount).
    Decreases on TicketClaimed (by claimedAmount).
    Tracked in USDM sub-units (same unit as pdPrizeAmount).

  Unresolved reserve (ppUnresolvedReserve):
    Reserve locked for unrevealed tickets: count * reservePerTicket.
    Increases on TicketIssued (+ reservePerTicket).
    Decreases on TicketRevealed (- reserveRelease).
    Decreases on TicketExpired (- reservePerTicket from average).

  Jackpot (ppLockedJackpot):
    Liquidity locked for jackpot. Subtracted from effectivePool.
    Threshold: ppJackpotThreshold. Active when effectivePool >= threshold.
    NOTE: Jackpot LOCK/WIN mechanisms are NOT implemented on-chain yet.
          Only the accounting fields exist.

  Circuit breaker (ppSuspendedClasses):
    Bitmask: bit 0 = Genesis, bit 7 = Class 7 (100 USDM).
    1 = suspended, 0 = active.
    Higher classes suspended first as solvency drops.
    NOTE: Circuit breaker ENFORCEMENT is NOT implemented in B1PrizePool
          validator. The field exists but no action checks it.

  Treasury flow:
    TreasuryDatum has 4 ScriptHash destinations:
      tdPrizeScriptHash    -> PrizePool (receives prize allocation)
      tdStakeScriptHash    -> Stake (receives stake allocation)
      tdReserveScriptHash  -> Reserve (receives reserve allocation)
      tdMaintenanceScriptHash -> Maintenance
    Percentages sum to 10000 (basis points).
    Threshold: minimum lovelace before distribution is allowed.
    All destinations MUST be ScriptCredential (protocol-controlled).
    Treasury does NOT validate USDM sub-units — it distributes lovelace.


4. TICKET LIFECYCLE
================================================================================

  The implemented flow (B1):

  Mint (MintPolicy.hs + mint.ts)
    - Counter UTxO consumed, advanced n -> n+1.
    - Serial NFT minted with name = counter value.
    - PrizeDatum created at PrizeValidator with status=Pending,
      beaconStatus=BeaconPending, pdPrizePoolHash set.
    - Ticket NFT sent to buyer.
    - NO Treasury payment in this tx (non-atomic limitation).

  Pending / BeaconPending
    - Ticket exists but beacon R not yet synced.
    - No economic action possible.

  Beacon Sync (PrizeValidator validateSyncBeacon)
    - Reads BeaconRegistry reference input.
    - Copies R (beacon value), mcHash, materiosContext from registry.
    - Transitions: beaconStatus BeaconPending -> BeaconReady.
    - PrizeDatum status stays Pending.
    - Value preserved.

  Reveal (PrizeValidator validateReveal)
    - Player reveals playerSecret.
    - On-chain: re-derives beacon, playerCommitment, ticketCommitment,
      symbols (via rejection sampling), tier, payout.
    - Transitions: status Pending -> Revealed, result/tier/amount frozen.
    - B1PrizePool: unresolvedTicketCount - 1, unresolvedReserve - release,
      pendingLiabilities + payout.
    - Cross-validated: PrizeValidator reads B1PrizePool input/output via
      pdPrizePoolHash and verifies accounting consistency.
    - Allowed even after expiry (historical result recording).

  Revealed
    - Payout crystallised. Claim window open until pdExpiresAt.

  Claim (PrizeValidator validateClaim)
    - Owner proves via ticket NFT ownership + signature.
    - Pays pdPrizeAmount lovelace to owner.
    - Transitions: status Revealed -> Claimed.
    - NFT NOT burned (constitution: keep as proof).
    - B1PrizePool: totalLiquidity - payout, pendingLiabilities - payout.
    - Cross-validated: PrizeValidator reads B1PrizePool input/output.
    - Expiry enforced: tx validity range must end <= pdExpiresAt.

  Claimed
    - Economic right exercised once. Ticket NFT retained.
    - No further economic action possible (status gate).

  Expiry (B1PrizePool TicketExpired)
    - For unrevealed tickets past pdExpiresAt.
    - B1PrizePool: unresolvedTicketCount - 1, unresolvedReserve - reservePerTicket.
    - PrizeDatum input must have status=Pending, payout=0.
    - PrizeDatum output: status stays Pending (or consumed entirely).

    (Non-atomic limitation: Treasury payment is separate.)

  Atomic: YES for NFT + PrizeDatum creation. NO for Treasury payment.

    - B1PrizePool UTxO (B1PrizePoolDatum)

  Reference inputs:
    - (none required for reveal itself)

  Outputs:

    - Ticket NFT back to owner

    - PrizeValidator (spending, verifies reveal logic + pool cross-validation)
    - B1PrizePool (spending, verifies TicketRevealed accounting)

    B1PrizePoolDatum: unresolvedTicketCount - 1, unresolvedReserve - release,

    pdTicketPolicy + pdTicketName match the NFT being spent.
    Owner identified via ticket NFT in inputs (PubKeyCredential).

  PrizePool update:
    B1PrizePool spent and re-created with updated accounting.
    PrizeValidator cross-validates the pool output.

  Atomic: YES. Both validators execute in the same transaction.

5.3  Claim

  Inputs:
    - Prize UTxO (PrizeDatum, status=Revealed, prizeAmount > 0)
    - B1PrizePool UTxO (B1PrizePoolDatum)
    - Ticket NFT UTxO (in owner's wallet, to prove ownership)

  Reference inputs:
    - (none)

  Outputs:
    - Prize UTxO (PrizeDatum, status=Claimed)
    - B1PrizePool UTxO (updated accounting)
    - Payout lovelace to owner
    - Ticket NFT back to owner (NOT burned)

  Validators:
    - PrizeValidator (spending, verifies owner sig, claim, pool cross-validation)
    - B1PrizePool (spending, verifies TicketClaimed accounting)

  Datum transitions:
    PrizeDatum: Revealed -> Claimed (no field changes except status)
    B1PrizePoolDatum: totalLiquidity - payout, pendingLiabilities - payout

  Ticket identity binding:
    Ticket NFT in inputs identifies owner. Owner must sign.

  PrizePool update:
    B1PrizePool spent and re-created. PrizeValidator cross-validates.

  Atomic: YES. Both validators execute in the same transaction.

5.4  Expiry

  Inputs:
    - Prize UTxO (PrizeDatum, status=Pending, payout=0)
    - B1PrizePool UTxO (B1PrizePoolDatum)

  Reference inputs:
    - (none)

  Outputs:
    - Prize UTxO (PrizeDatum, status=Pending unchanged)
    - B1PrizePool UTxO (count - 1, reserve - reservePerTicket)

  Validators:
    - B1PrizePool (spending, verifies TicketExpired)

  Datum transitions:
    PrizeDatum: unchanged (Pending stays Pending)
    B1PrizePoolDatum: unresolvedTicketCount - 1, unresolvedReserve - reservePerTicket

  Atomic: YES.


6. SECURITY / TRUSTLESSNESS AUDIT
================================================================================

  exact Prize UTxO binding:
    YES — PrizeValidator uses pdPrizePoolHash to locate B1PrizePool UTxO,
    findB1PrizePoolOutput/readPoolInput verify it exists as input+output.
    PrizeValidator also verifies the Prize output via findSingleContinuing.

  singleton PrizePool enforcement:
    PARTIAL — findSingleContinuingDatum in B1PrizePool ensures exactly one
    output to the same script. But there is no on-chain check that only one
    B1PrizePool UTxO exists globally. An attacker could create a second
    PrizePool UTxO at the same address. The singleton property relies on
    the off-chain builder selecting the correct UTxO.

  payout <= EffectivePool:
    NO — The B1PrizePool validator does NOT explicitly check that
    ppPendingLiabilities + payout <= ppTotalLiquidity - unresolvedReserve.
    It relies on solvencyInvariant post-condition. A payout that breaks
    solvency would be caught by solvencyInvariant on the output datum.
    This IS enforced: solvencyInvariant checks effectivePool >= 0 on next.

  deterministic reserve accounting:
    PARTIAL — On TicketIssued, reservePerTicket is redeemer-supplied (only
    checked > 0). On TicketRevealed, reserveRelease is redeemer-supplied
    (only checked >= 0). The off-chain code computes correct values, but
    a malicious tx could supply different values. The solvencyInvariant
    constrains the damage but does not enforce protocol-correct values.

  no arbitrary transaction-supplied accounting:
    NO — reservePerTicket (TicketIssued) and reserveRelease (TicketRevealed)
    are supplied by the transaction. The on-chain code cannot derive them
    from protocol state. This is a trustless-accounting gap.

  no USDM/lovelace unit mixing:
    NO — B1PrizePoolDatum fields are documented as lovelace (ppTotalLiquidity
    comment: "Total ADA held by the PrizePool (lovelace)"), but payouts
    (pdPrizeAmount) are in USDM sub-units. FundTreasury measures actual
    lovelace increase. TicketClaimed subtracts USDM sub-units from
    totalLiquidity. This only works when 1 ADA ≈ 1 USDM. On mainnet with
    a different rate, conversion is required.

  owner authorization:
    YES — validateClaim checks ticket NFT owner via ticketOwnerPkh and
    verifies pkElem pkh (txInfoSignatories info).

  double-claim prevention:
    YES — PrizeDatum status transitions Pending -> Revealed -> Claimed.
    Claim requires status == Revealed. After claim, status == Claimed,
    and claim check fails.

  NFT retention:
    YES — Constitution: NFT is NOT burned on claim. Ticket NFT returns
    to owner. validateClaim does not require a burn mint.

  expiry enforcement:
    YES — claimBeforeExpiry checks tx validity range upper bound <=
    pdExpiresAt. Expired tickets cannot be claimed.

  randomness / rejection sampling:
    YES — generateSymbols uses SHA-256 + rejection sampling (byte 255
    rejected). Deterministic from symbolsSeed. Same logic in Plutus and
    TypeScript.

  commitment binding:
    YES — ticketCommitment binds ticketId, playerCommitment, gameVersion,
    ticketNonce, priceUsdm, beaconTarget via SHA-256. Verified on-chain
    in validateReveal. Player commitment verified against playerSecret.

  jackpot accounting:
    PARTIAL — Fields exist (ppLockedJackpot, ppJackpotThreshold). The
    jackpotActive helper computes threshold check. But no action on-chain
    actually modifies ppLockedJackpot or triggers jackpot payouts.
    Jackpot is ACCOUNTED but NOT IMPLEMENTED.

  circuit breaker enforcement:
    NO — ppSuspendedClasses bitmask field exists in B1PrizePoolDatum.
    But NO validator action checks or modifies this field. It is
    DOCUMENTED ONLY.

  Treasury protocol-controlled destinations:
    YES — TreasuryDatum stores 4 ScriptHash destinations. Treasury
    validator verifies all outputs go to ScriptCredential addresses
    matching the datum. No personal wallet destinations allowed.

8. REMAINING B1 BLOCKERS
================================================================================

  1.  CRITICAL — gameFlow.ts PrizeDatum field count mismatch
      File:    src/gameFlow.ts:225
      Function: decodePrizeDatum()
      Issue:   Checks fields.length !== 20, but PrizeDatum has 21 fields
               (pdPrizePoolHash was added at index 18, shifting pdIssuedAt
               to 19 and pdExpiresAt to 20).
      Effect:  ALL gameFlow functions (syncBeacon, revealPrize, claimPrize)
               will throw "PrizeDatum not decodable" on any real PrizeDatum.
      Fix:     Change check to fields.length !== 21. Update field index
               comments at lines 195-215.

  2.  CRITICAL — USDM/lovelace unit mixing in B1PrizePool
      File:    plutus/B1PrizePool.hs (all actions), plutus/Types.hs:168
      Issue:   ppTotalLiquidity is documented as lovelace ("Total ADA held"),
               but TicketClaimed subtracts USDM sub-units (pdPrizeAmount)
               from it. FundTreasury adds actual lovelace. These are
               different unit systems. The arithmetic only works when
               1 ADA ≈ 1 USDM.
      Effect:  On mainnet with a different ADA/USDM rate, accounting will
               be incorrect. Payouts will not match ADA value.
      Fix:     Either (a) change all B1PrizePoolDatum fields to USDM sub-units
               and add a conversion layer at Treasury/Claim, or (b) change
               payout calculation to produce lovelace directly.

  3.  HIGH — reservePerTicket is redeemer-supplied (TicketIssued)
      File:    plutus/B1PrizePool.hs:227-249
      Issue:   reservePerTicket comes from the redeemer. On-chain only
               checks > 0. A malicious tx could supply an artificially
               low or high reservePerTicket, manipulating pool accounting.
      Effect:  Trustless-accounting gap. Pool solvency may be maintained
               but reserve accuracy is not guaranteed.
      Fix:     Derive reservePerTicket from protocol config on-chain, or
               require it to match pdPriceUsdm * some protocol constant.

  4.  HIGH — reserveRelease is redeemer-supplied (TicketRevealed)
      File:    plutus/B1PrizePool.hs:252-273
      Issue:   reserveRelease comes from the redeemer. On-chain only
               checks >= 0. Same trustless-accounting gap as #3.
      Effect:  Reserve accounting may drift from actual values.
      Fix:     Derive from ppUnresolvedReserve / ppUnresolvedTicketCount
